1

What cronoaudit does, and for whom

cronoaudit reads a schedule, checks whether it holds together, measures what is done against what was planned, projects what comes next, and writes a report in which every figure says where it came from and how to reproduce it. It looks for one specific kind of failure: the arithmetic is right, every term is right in its own source, the result is plausible, nothing errors, and the number means nothing.

For whom

For whoever has a schedule in front of them and has to say whether it holds: the schedule received from another party, the one produced in-house, or the one under their responsibility to update. The reader may sit in a contractor, a supervising body, a regulator, a consultancy, or be studying. The tool does not distinguish the role of whoever uses it; it distinguishes the file. The planner who has to deliver a schedule that passes, the engineer auditing what was received and the manager who needs a cycle report for the board use the same report.

The manual assumes no prior knowledge of the concepts. Chapter 2 explains each one from scratch. Readers who already have them can go straight to chapter 3.

What goes in and what comes out

Input
The schedule exported from MS Project as XML, which is Project's own documented format. One file for the critical review; two files, previous and current, for the cycle comparison.
Output
A self-contained HTML report with no external reference, which opens in any browser and prints to PDF. Beside it, one JSON file per analysis, for whoever wants the data outside the report.
Language
The schedule's. The tool detects it from the content and writes the report in Portuguese or English. It can be forced.
Requirements
Python 3.9 or later. Nothing else. No data leaves the machine.

The eight answers in the report

SectionQuestion it answers
Verdict and findingsDoes the logic hold? Which dates have elapsed, moved, or are misreported?
S-curveWhere should the contract be, where is it, and does the tool's figure match Project's?
Progress by groupDid progress happen where the money is?
ProductivityAt three rates, when does each activity in progress finish, and does it enter the critical path?
Network qualityDoes the schedule work as a model, before any discussion of dates?
Looking forwardWhen does it really finish, what do the next weeks demand, and where does the pace fall short?
ForensicsWhere did each milestone's delay come from, by which path, and when did it start?
Cycle comparisonWhat changed since the last delivery: execution, replanning, or the reference itself?

What it does not do

It does not read Primavera P6: the method transfers, but nothing was measured in that format. It does not produce a contractual delay claim: the forensics reconstruct the mechanism, and a claim needs contemporaneous records and a formal method. It does not certify against the DCMA standard: the fourteen metrics are implemented and labelled as an implementation. And it never invents a distribution, a default value or a figure the file does not carry. Chapter 12 covers this in detail.

2

Concepts this manual assumes

Every concept below appears in the report. If one is new, read its box before going on. If all are familiar, this chapter is a vocabulary reference.

The schedule as a network

A schedule is not a list of dates. It is a network: each activity has predecessors, which must happen before it, and successors, which depend on it. The link type says how: finish-to-start is the common one, the successor only starts when the predecessor finishes; start-to-start, finish-to-finish and start-to-finish are the other three. A link can carry a lag, a mandatory wait, or a lead, a permitted overlap.

When the scheduling tool recalculates dates, it walks this network. If the network says one thing and the works do another, every calculated date rests on logic that is not being followed. That is why the report checks the network before any date.

Baseline

The baseline is a copy of the plan saved at a certain moment: dates, durations and costs as they were when the plan was approved. Everything the report calls variance, delay or pull-forward is measured against it. MS Project keeps up to eleven baselines, numbered 0 to 10, and a schedule that has grown may hold the current one in a slot that is not the default. Which slot counts is a choice, and cronoaudit makes it from the data, not from a field that declares and is not confirmed.

Status date

The date up to which progress is valid: the schedule's "today". Every comparison of planned against actual is made at it. A file without a status date cannot be analysed honestly, and cronoaudit refuses to assume today's date instead, because that would change the answer every day the analysis was repeated.

Calendar and working day

Each activity has a calendar, which says which days and hours are working time. That is where holidays, the shift, the five- or six-day week and the weather reserve live, the days the works do not work because of rain. Two activities in the same schedule can have different calendars. Every duration, variance and window in the report is counted on the activity's own calendar, because counting in calendar days, or on the project calendar, gives wrong numbers in silence.

Physical percent and percent complete

They are two different fields. Percent complete is duration: how much of the activity's time has passed, and Project computes it on its own from actual dates. Physical percent is declared by a person and measures how much of the work is out. One says how much time passed; the other, how much was delivered. Earned value uses the physical one. Swapping one for the other changes the result with nothing changed on site.

Earned value and the S-curve

Earned value is each activity's baseline cost multiplied by its physical percent. Summed, it is how much of the budget has been "earned". Planned value is how much should have been earned by the status date, according to the time-phased baseline. The S-curve is the cumulative chart of both over time: planned and earned, and the gap between the curves is the delay in money. The schedule performance index, SPI, is earned divided by planned.

Float and critical path

An activity's total float is how much it can slip without moving the project finish. Zero float means any delay there pushes the end: the activity is critical. The critical path is the chain of critical activities from start to finish. An activity with float can slip until it consumes it; after that, it enters the critical path. Project computes float, early and late dates and the critical flag; cronoaudit reads those fields rather than recomputing them.

Earned Schedule

Classic earned value measures schedule in money, and that has a defect: at the end of the project earned always reaches the budget, so the schedule indicator goes to 1.0 even on a project a year late. Earned Schedule measures schedule in time: it asks on what date the planned curve reached the value earned today. That date, compared with the time elapsed, gives a schedule efficiency and an independent finish, which is set against the finish the schedule projects. Chapter 8 details the formulas.

Productivity by resource

A material resource, such as cubic metres of cut, has planned, executed and remaining quantities per activity. Productivity is quantity per working day. Comparing the practised rate with the required one says whether the activity finishes when the schedule says. cronoaudit reads the quantities from the file's own assignments, with no custom field.

The reference question

An indicator that compares planned with actual has two halves. If they are measured against different references, another baseline slot, another instant, another population, another unit, the difference between them means nothing, and the number comes out plausible. It is the failure cronoaudit looks for everywhere. The question that finds it: are all the terms of this calculation measured against the same reference?

Installation and first run

cronoaudit is an Agent Skill: a folder with instructions for an assistant and the programs that do the work. It installs by copying that folder to where the assistant looks for skills. The installer does that for every assistant at once.

Install with one command

On macOS or Linux, in a terminal:

curl -fsSL https://raw.githubusercontent.com/Holiv/cronoaudit/main/install.sh | bash

On Windows, in PowerShell:

irm https://raw.githubusercontent.com/Holiv/cronoaudit/main/install.ps1 | iex

The installer downloads the package, copies the skill to the two directories that, together, every assistant reads, and runs the tool's internal test as proof of installation. At the end it shows where the skill went and how to invoke it. Restart the assistant after installing, because skills are read at the start of each session.

~/.claude/skills/cronoauditClaude Code, OpenCode, Cursor
~/.agents/skills/cronoauditCodex, Gemini CLI, Cursor, GitHub Copilot, VS Code, OpenCode

Each assistant also has a native install path: npx skills add Holiv/cronoaudit -g in any client of the format, gemini skills install with the repository URL in Gemini CLI, Codex's skill installer, Cursor's Remote Rule, and the Claude Code plugin. The repository README keeps the table current.

With no assistant at all

The tool works without artificial intelligence. Clone or download the repository and run the program directly. Everything is produced except the written executive synthesis and the customisation interview, which are the two parts that depend on an assistant.

git clone https://github.com/Holiv/cronoaudit
python3 cronoaudit/skills/cronoaudit/scripts/review.py delivery.xml

Exporting the schedule

The .mpp file is a closed proprietary format. cronoaudit reads the XML that Project itself exports, which is a documented format and carries everything the analysis needs: tasks, links with lag, the eleven baselines, calendars, custom fields, assignments and the time-phased data.

In MS ProjectFile, Save As, and under file type choose XML Format. Keep the XML beside the .mpp. When the XML is sent with the .mpp by whoever produces the schedule, this step disappears from the routine.

There is an optional path to read .mpp directly, through a Java library, for whoever has it installed. It is never required.

First run

python3 ~/.claude/skills/cronoaudit/scripts/review.py delivery.xml

On a schedule of six thousand activities the run takes under a minute. The terminal shows the summary: baseline slot used, threshold, population, counting convention, and the list of nine findings with each one's activity count. Next to the input file sit the results.

Inside an assistant: how to start the conversation

With the skill installed, no command needs to be remembered. The assistant reads the skill's instructions, runs the programs, reads the results and talks about them. The figures always come from the programs; the assistant orchestrates, interprets and writes. What follows is the most direct way to begin.

Where to open

The assistant reads the local disk, so it has to know where the file is. Two equivalent ways: open the terminal in the folder that holds the XML and start the assistant there, or start anywhere and give the full path in the first message. When the folder holds more than one XML, the message should name the file; the assistant is instructed to list the files and ask which one to use, never to choose silently.

The first message

cronoaudit, review the schedule delivery-september.xml
cronoaudit, analyse the schedule at ~/Schedules/2026-09/delivery.xml
cronoaudit, compare previous.xml with current.xml
cronoaudit, analyse delivery.xml and save the results in ~/Reports/september

The skill's name at the start of the message makes sure the assistant loads it. From there the language is free.

What happens next

The analysis runs once. It and the report are the same command: whenever the analysis runs, the HTML report and the JSON files are written beside the XML, or in the folder named in the message. The assistant states the report's full path in its first reply. After that the conversation continues over the data already written, point by point, without running again. Nothing is sent anywhere; the files stay where they were written.

The report does not have to be opened for the conversation to happen. A finding, a rate or a milestone can be discussed for an hour before the HTML is opened, or it may never be opened. The executive synthesis is written only when asked for.

Without an assistant the tool is entirely free: Python and the command produce the full report with the rule-built readings. With an assistant it depends on the assistant's plan. As of this edition, Claude Code is not part of Anthropic's free plan and requires a subscription or API credit; Gemini CLI and GitHub Copilot offer free tiers that read the Agent Skills format. Verify the tool before trusting it

python3 ~/.claude/skills/cronoaudit/scripts/test_checks.py

The test runs the tool over two synthetic schedules. On the positive one every check must fire. On the negative one every check must stay silent. Without the second half a clean result is worth nothing: a probe that cannot fire reports zero findings on a broken file as readily as on a sound one.

An equivalent implementation inside Project

The same method exists as macros that run inside MS Project, marking activities in the schedule itself and generating the same report. It is a separate product by the same author, and cronoaudit does not depend on it. The two implementations follow the same rule specification, and one's count has to match the other's on the same file.

The report, section by section

The report is a single HTML file. It opens in any browser, works offline, prints to PDF with one button, and switches between light and dark themes. Activity tables are collapsed, so the report does not open as a wall of rows; printing expands them.

Cover and verdict

The cover carries the file, the number of leaf activities, the status date and the baseline cost. The verdict shows cumulative physical progress weighted by cost, beside a fixed text on how to read those numbers, and the first Reading block: sentences generated by rule from this analysis's figures. A red notice appears when activities sit in violated logic, and says to settle that before discussing any date.

When an executive synthesis has been injected, it appears right below the cover, with the name of whoever wrote it and the time, so prose is never mistaken for measurement.

Cards and index

One card per finding, with the count and the severity colour. The index lists the views and the findings with code, title, subtitle, count and severity, and each row leads to its section.

checkG, Fa symptom to inspect, not a finding to report

The findings

Each finding is a block with code, severity, title and plain-language subtitle. Inside, three fixed blocks: problem, impact and solution. Then the criterion with the counting convention, where it came from, with the Project columns, and how to reproduce it in the tool. Finally the activity table, collapsed. Only the visible row number identifies an activity, because it is the only identifier a person can find on screen. In the network findings the table shows the explicit pair, successor and predecessor, with the link type and the reason.

Conventions

The last section lists what the report assumed: the baseline slot and why it was chosen, the threshold and its unit, the tolerance, the population, the counting convention, how working days were counted, where the percentage comes from, the detected language and how confident the detection was. Nobody has to guess anything.

The reading layer

Every section opens with sentences generated by rule from its own figures. They say what the data supports and nothing more; if a figure is missing, the sentence does not appear. It is what lets the report be handed to someone who was not in the room. The executive synthesis is something else: a written text, injected with author and time, which chapter 10 explains.

5

The nine checks

Each check has a stable code, which stays the same when the implementation changes. Without that a problem cannot be discussed across weeks. The order matters: network first, then dates, then reporting.

Population and cross-cutting rules

Every check looks only at leaf activities, active and not external. Summaries stay out, because they would count their children twice. Milestones are in everything except G.

Pending reporting migrates firstA predecessor at 100% physical with no actual finish is a reporting defect, finding P. Its links are not evaluated for A1 or A2. Without this rule, a reporting problem would be reported as an execution problem, and the conversation with whoever executes would start by accusing the wrong thing.

A1 · Out-of-sequence execution

A successor started while the predecessor had not finished, or finished after the successor's start beyond what the link allows.

Problem
The network describes an order that execution does not practise.
Impact
Every forecast date is computed on a false premise. And the delay of stalled predecessors stops propagating to milestones, because the successors have already been delivered: the plan looks healthy at the end because it is broken in the middle.
Solution
Settle before discussing any date. Either the link is wrong, or the sequence was broken on site and the consequence enters the forecast. Do not delete the link to silence the warning: it is the only record that the order was not followed.

The criterion evaluates the four link types, with actual dates, on the successor's calendar, honouring lag. An overlap covered by a lead is not flagged. Pairs with both activities complete leave the count, by decision, and are recorded in the data with the overlap in days, because the history of out-of-order execution is evidence for the forensics.

LinkSuccessorPredecessorResult
FSactual start, not completeno actual finishA1, predecessor not finished
FSactual start, not completefinished after the start, beyond the leadA1, overlap beyond lead
FScompletecompleteoutside the count, recorded

Both ends of the violated link are marked, and the report counts three ways: distinct activities, as successors, as predecessors. How many activities have the problem depends on how they are counted, and diverging from the convention of the other party's tool hands them the argument.

To reproduce in Project

Group by predecessor and filter by Actual Start populated. Mark the pair and inspect the link in the Gantt.

A2 · Total inversion

A successor is complete and the predecessor never started. It is the extreme form of a broken sequence, and it is unanswerable in a meeting. Either the sequence was invented for the plan, or the progress landed on the wrong activity. Check pair by pair and record which, because the answer varies between pairs.

To reproduce

Filter by Actual Finish populated and check the Actual Start of each predecessor.

H · Forecast elapsed with no actual

A forecast start is in the past with no actual start, or a forecast finish is in the past with no actual finish. The plan says it happened; nothing in the file says it happened. Every successor is projected from a date that already failed to hold. Two possibilities with different answers: the work happened and was not recorded, or it did not happen and the forecast must move. Leaving it is the only wrong option.

E · Pulled forward and never started

The forecast finish moved earlier than the baseline by 30 working days or more, on the activity's calendar, and the activity never started. Progress pulled earlier with no execution behind it is a plan change dressed as performance, and in aggregate it can offset real delay elsewhere. Ask what changed to justify the date. If nothing did, the forecast is optimistic and should go back.

C · Delayed beyond the threshold

The forecast finish moved later than the baseline by 30 working days or more, on the activity's calendar. Completed activities stay in the list on purpose: consummated delay is information. It is the finding the other party expects and the easiest to contest, which is why it needs the reproduction attached. Read it with the weight distribution: the same number of delayed activities means different things depending on the budget share they carry. The float column says how much margin is left.

Threshold in working daysThe 30 days are counted on the activity's own calendar, not in calendar days nor on the project shift. On a six-day week, 30 working days are about 35 calendar days. The unit is declared in the conventions section and adjustable through the profile.

G · Duration inconsistent with the window

The duration does not match the working time between start and finish, measured on the activity's own calendar, with partial first and last days. G is a thermometer, not a finding: it says something was edited inconsistently, not what. Start anchored on the actual date with the remainder pushed, a typed date over a computed one, a constraint fighting the logic. Use it to choose what to inspect, looking at the largest differences first. Never report it alone.

B · Milestone with no deadline

The milestone has no Deadline set, so nothing in the file makes its date binding. Without it the milestone shows comfortable float even with the contractual date passed, because the schedule was never told the date mattered. A deadline is not a constraint: it moves nothing, it only reveals slippage. Register contractual dates on the milestones that have them; it changes no calculation and makes every following report tell the truth about float. B is optional by default, because not every organisation practises it; the profile promotes it to a finding.

F · In progress at zero percent

Actual start, no actual finish, and duration percent complete at zero. On a schedule reported by physical percent this fires a lot, because the duration percent is not maintained; that is why it is treated as a check. On a schedule reported by duration, it is the real signal of a stalled activity.

P · Pending reporting

One hundred percent physical with no actual finish date. It is a reporting defect, and the distinction decides who the conversation is with. Kept among the network findings, it would accuse the team of executing out of sequence when the work was done and only the date is missing. Enter the actual finish. Until then the activity stays deliberately out of the network findings.

Network quality

Does this schedule hold as a model, before any discussion of dates? Section V7 answers with the mechanical metrics of the DCMA 14-point model, each with its formula in words, declared population and quoted threshold so it can be contested, plus what a planner asks of any schedule.

Implementation, not certificationThe thresholds come from a published model and are quoted so they can be discussed. How to read it

Read Q1, Q2, Q5 and Q7 before any date. A schedule that fails them is not a model of the works, and every date it produces is a number with no basis. Q6 and Q8 say whether it can be controlled. Q11 and Q14 say whether it was met. Beyond the fourteen, the report shows summaries with links, which should not exist, milestones with no deadline, the number of incomplete critical activities, and whether the critical chain reaches the final milestone, which is the test of the network being whole.

On the example schedule

An activity pinned by a must-finish-on constraint appears in Q5. A link with a three-day lag appears in Q3. A summary carrying a link is flagged. The baseline execution index falls below the floor because a due activity did not finish.

7

Productivity and trend by resource

Section V6 answers, for every activity in progress with a quantity, when it finishes at the actual rate, and what that does to the baseline and the critical path. Everything comes from the file's own assignments; no custom field is required.

Where the quantities live

For a material resource, Project stores the quantity in the work fields, as hours of a duration. An assignment with 10,567 hours of work on a resource labelled m³ is 10,567 m³. The same rule gives executed, remaining, baseline planned and executed per day. An assignment with no resource cannot be trended, and the report counts how many there are.

Three rates, not one

One rate alone is not a fair reading: a cut activity hit by a fortnight of rain shows a rate that says nothing about the crew.

RateHowWhat it answers
ownexecuted on this activity divided by working days elapsed since its actual start, on its calendarwhat is happening here, rain included
globaleverything executed by the resource on all fronts divided by the working days those assignments tookthe fair scenario, which dilutes a bad fortnight
recentthe last 30 days of the resource's executed blocks divided by the window's working daysthe pace now, not the average of months

The own rate divides by elapsed days, including days when nothing came out. A crew that produced on eight of ten days practised the ten-day rate. The planned rate also comes out, baseline quantity over baseline duration, and two required rates: remaining over working days to the forecast finish, and to the late finish.

Four dates, three verdicts

The remainder runs over each rate, in working days of the activity's calendar from the status date, and lands against four dates: forecast finish, baseline finish, late finish, which the file already carries with the float built in, and the projected finish.

Projected landsVerdictMeaning
by the forecastaheadnothing to do
after the forecast, by the baselinereprogramthe forecast is wrong, the baseline is not threatened
after the baseline, by the late finishbaseline delay, float absorbsno impact on the end date yet; the column says how many float days remain
after the late finishenters the critical pathon the date shown, before the schedule shows it
One case read end to end

Baseline on 30 September, forecast on the 26th, twenty days of float. If the rate projects 28 September, it is reprogram: the forecast slips, the baseline does not. If it projects 2 October, the baseline slips two days and eighteen days of float remain: no impact on the end date. If it projects more than twenty days beyond the forecast, it enters the critical path, and the date that happens appears in the table.

Thin evidence

A rate built on a few days, or on a tiny share of the planned quantity, projects absurdity with complete ease: a resource at two percent executed "finishes" in 2031. The rate is reported, because it is what the data says, but it is flagged as thin evidence when it has under ten days of data or under two percent of the planned quantity, and the verdict carries the flag. Executed derived from physical percent, rather than posted quantity, is also flagged as inferred. Read those as a question, not a verdict. The thresholds are adjustable through the profile.

Contracted productivity

If the organisation keeps a contracted productivity per crew in a custom field, the profile can point to it and it appears as a comparison column beside the rates. It is an optional layer, never a requirement.

8

Looking forward and looking back

Section V8 answers when the contract really finishes and what the next weeks demand. Section V9 answers where each milestone's delay came from and by which path. Both use only what the file already carries, and every reading says what it was built on.

Earned Schedule

Classic earned value measures schedule in money, and at the end of the project the indicator goes to 1.0 on a project a year late. Earned Schedule measures schedule in time. Take today's earned value, go up to the planned curve and read the date the curve got there. That date is ES: where the plan said we would be.

QuantityFormulaReads as
ESdate at which cumulative planned equalled today's earned, interpolated inside the monthwhere the plan said we would be
ATdays from the first planned day to the status datetime elapsed
SV(t)ES minus ATdays behind the plan; negative is behind
SPI(t)ES divided by ATschedule efficiency; 0.90 is ten percent slower than the plan
PDfirst planned day to the last baseline finishplanned duration
IEAC(t)PD divided by SPI(t), as a date from the first planned dayindependent finish at this efficiency
TSPI(PD minus ES) divided by (PD minus AT)efficiency the remainder needs to finish on the date

TSPI is the meeting number. Above 1.0 the remainder must run faster than the plan. Above 1.10 the literature treats it as unrecoverable, because no works sustains ten percent above plan for long. It turns "we are late" into "we need this much more per week, and that is or is not possible".

The limit, stated in the reportIt is an aggregate, cost-weighted measure, and it does not see the critical path: a mass of non-critical activities late shows behind while the end date holds, and the reverse too. So the independent finish never replaces the schedule's own finish. It sits beside it, and the gap between the two is the conversation. It inherits everything the planned curve inherits: the slot, the earned-value method, execution ahead of the baseline window.
On the example schedule

Earned is far behind planned, and ES falls more than a hundred days before the status date. Schedule efficiency is below 0.2 and TSPI above 1.7: the remainder would need to run seventy percent faster than the plan. The report writes that as a question about the schedule, not as a sentence.

Look-ahead

Four and eight weeks from the status date: what must start and what must finish, by group, weighted by baseline cost; the earning the file plans for the window, pro-rata from the phased curve; and the earning the last two months' practised rate would deliver. One word says whether the planned measurement of the window is reachable.

Rates by group

Percent earned per week to date, from the group's first earning, against the percent per week the remainder needs to land on the group's last baseline finish. The ratio required over practised gives one word per group: on pace, stretch, out of reach.

Milestone bands

The distribution of finish slippage, current finish minus baseline finish in calendar days, across started or due activities in this snapshot, applied to each future milestone's current finish as P50 and P80. Empirical, not a simulation with an invented premise. A series of snapshots replaces it with observed cycle-to-cycle movement.

Rain exposure

Remaining cost spread evenly over each activity's current span from the status date, read against the months its own calendar reserves for bad weather, a month with four or more non-working exceptions. Reported now and again with everything slipped thirty days, because slipping into the reserve is how a small delay becomes a large one. The spread is inferred; the reserve months are measured.

Forensics: driving path per milestone

Where did the delay come from, by which path, and when did it start? From each future milestone the tool walks back through the predecessor that actually drives each start, the one whose link instant plus lag lands latest on the successor's calendar, until it reaches a finished activity, because the past drives nothing, or an open end.

Each node on the chain carries its finish variance against the baseline in working days. The origin is the deepest node on the chain still carrying at least five working days of variance: walking back from the milestone, variance is inherited from the driver, so the last node that still has it is where it entered. The delay gets a name and a row number, not an aggregate. The report also says which activities originate delay on the most milestones, because one name can be the root of a dozen slipped dates, whether each chain reaches started work, and whether it dies on an open end, which is finding Q1 seen from the milestone's side.

Not a delay claimA contractual claim needs contemporaneous records and a formal method, such as the AACE recommended practices on forensic schedule analysis. This reconstructs the mechanism from the file's dates, links and calendars, with reproducible evidence, to sustain the meeting and the notification. The contractual conversation happens in real time, with each organisation's reality.
On the example schedule

There is a future contractual milestone with twelve working days of variance. The driving chain has three nodes, and the origin is the milestone itself: the variance did not come from any predecessor with delay of its own, which points to a typed date or to a chain broken before it.

Calendar forensics

A weather reserve registered for one year while the activities on that calendar execute in another embeds optimism nothing in the file announces: the month gets its full working days instead of its real ones. Per calendar in use, non-working exceptions per year against activity-days per year, with two flags: years with activities and no reserve while the calendar has reserve in another year, and years with reserve and no activities.

Execution pattern

Out-of-sequence execution by the month the successor started, counting the A1 pairs and the both-complete pairs recorded outside it. And the distribution of start slippage against the baseline across started activities: P20, P50, P80, how many started early, how many late.

With a previous snapshot

Float consumed per activity and per group, total float before minus total float now, in working days: float that disappears while dates hold is delay still invisible. Activities that became critical this cycle. And each milestone's movement between the snapshots, attributed to what moved on its driving chain through the comparator's three signals: execution, replan or moved reference, with the majority reading as the attribution.

9

Cycle comparison

The single-file review asks whether the schedule holds together inside. Comparing two asks something else: what moved since the last delivery, and was it the works that moved or the plan?

Input

python3 ~/.claude/skills/cronoaudit/scripts/review.py previous.xml current.xml

Two snapshots of the same schedule: the previous version and the current one. Not two different schedules, and not a schedule against an application's database. Each schedule compared against itself, which is what makes the reading defensible. With two files come the comparison and the review of the current file, deliberately: comparing two files that do not hold together is comparing two wrong answers.

Each snapshot needs a status date and a saved baseline. Without a baseline there is no planned half and the deviation decomposition has no denominator.

Matching an activity across versions

First by the stable unique identifier, not the row number, which renumbers freely. Failing that, by name plus WBS path. What does not match falls into two classes, and only two: inserted, present in the current with no pair in the previous, and removed, present in the previous and never matched. A renamed activity that also moved branch is indistinguishable from a removal plus an insertion, and pretending otherwise manufactures a third category that cannot be verified. The report shows the count for the reader to judge.

A false pair is worse than a missed pairA pair that does not match lands in the unmatched list, where somebody looks. A pair matched wrongly produces a date movement, a deviation and a trend entry for two activities that have nothing to do with each other, all plausible. Summaries and milestones stay out of deviation and trend: summaries would double-count their children, and milestones have no duration.

The three signals

SignalReading
dates moved and actual dates are presentexecution
dates moved, no actual datesreplan
baseline dates movedreference moved

The third is the one to look at first. When the baseline changes between two cycles, the basis of the comparison moved underneath it, and every deviation that straddles the change is measured against two references. Report it as a finding about the report, not as performance. The second is where the conversation between the parties is decided: a forecast rewritten with no execution behind it is a plan change, legitimate, but it has to be visible as one, otherwise the next cycle starts from a reference nobody agreed to.

The deviation decomposition

For each leaf activity with baseline cost above zero, the contribution is its earned minus planned divided by total baseline cost, in percentage points. The contributions sum to the aggregate, and those that round to zero are dropped, because a list of zeros hides the ones that matter. When the sum does not match the movement, the residue appears as unexplained, with the number, instead of vanishing. The denominator is declared: summary total or sum of the leaves.

It is the operational answer to the aggregate problem. A positive aggregate progress can be out-of-sequence work covering activities that should be complete and sit at zero; the decomposition is what lets that be read on the spot.

One function, called twice

Both snapshots' indicators are computed by the same function, called twice, and not by two paths that happen to agree. If the previous cycle's figure were computed differently from the current one, the difference between them would be a reference artefact, and it would read as performance. The two halves are not verified to agree; they are built so they cannot disagree.

What comes out

A cycle report and a JSON, named after both files. Inside: both snapshots' general indicators by the identical rule, the movement in points, the per-activity decomposition that sums to it, the unexplained residue, the trend with the three-signal reading per activity, the moved baselines, the inserted and removed, and the warnings: a baseline that changed slot between cycles, for instance, comes out as a warning.

On the example pair

Two activities moved dates: one with actual dates, read as execution; another without, read as replan. One had its baseline changed, and the report issues a moved-reference warning before any performance figure. The decomposition has one row, which sums to the movement.

Limits, labels and what the tool does not decide

A defensible report says what it does not know. This chapter gathers the tool's limits, the labels it uses to separate measurement from inference, and the judgements that stay with the person.

The three labels

LabelMeansExample
measuredread directly from the file, reproducible by anyone with the same filethe A1 count, the planned curve, the number of calendars in use
inferredderived by a declared rule, from measured dataexecuted derived from physical percent; the even spread of the remainder in the rain exposure
reportedcomes from a documented record, not from this analysis's measurementproduction-use results cited in the method references

The label travels with the figure in the report and the JSON files, and an inferred figure is never presented as measured.

What the tool refuses to do

  • Assume today's date when the file has no status date. The analysis stops and says why.
  • Invent the planned half when no baseline slot carries cost. Without a baseline there is no adherence.
  • Approximate the two quality metrics a file cannot answer. Q12 and Q13 come out as not computable.
  • Guess a distribution. The milestone band is empirical, from observed slippage; the rain exposure uses an even spread and says so.
  • Match activities by similarity. Only stable identifier or name plus path. The rest is inserted or removed.
  • Replace the schedule's finish with Earned Schedule's independent finish. The two sit side by side.

Judgements that stay with the person

G is a thermometer: use it to choose what to inspect, never report it alone. The physical percent may have been typed, and everything computed from it inherits that; the report says which field it used. The baseline slot is elected from the data, because the field that should declare it is not dependable; check it with whoever owns the schedule. If the calendar table shows a shift or week different from what the works practise, every date inherits the error. A thin-evidence rate is a question. A forensic origin that lands on the milestone itself points to a typed date or a broken chain, and someone has to open the file.

Formats and scope

MS Project XML is the measured format. Reading .mpp and Primavera P6 through a Java library is optional and unverified. The tool does not produce a contractual claim, does not certify against a standard, and does not replace the meeting: it delivers what the meeting needs so it does not turn into an argument about the arithmetic.

13

Frequently asked questions

The report flags zero on everything in a file I know has problems

Look at the population line in the conventions. Summary-only files, or files with everything marked external, have no leaves to test. And run the internal test: if the positive fixture does not fire, the installation is broken.

cronoaudit's count does not match my macro's

First check the convention: distinct activities, as successors or as predecessors give three numbers for the same problem, and the report shows all three. Then check the baseline slot and the threshold. Finally, the both-complete pairs: cronoaudit leaves them out of A1 and records them separately. The macro implementation follows the same specification, and on the same file the counts have to match, convention by convention.

Earned value does not match Project

The reconciliation at the foot of the S-curve says on how many tasks it matches and classifies those that do not. The common cause is execution ahead of the baseline window: Project only credits the phased cost when the status date reaches the window, and the method credits cost times physical at once. Both are right against their own instant. If the difference is something else, the slot may be wrong.

Why is the report in English when the schedule is mine

The language is detected from the file's content: activity names, calendars, title. A schedule with English names produces an English report. Force it with the language option or through the profile.

Can I change the 30-day threshold

Yes, through the command-line option or the profile. The report then declares the new value in the conventions. It counts in working days of the activity's calendar, so thirty working days on a six-day week are about 35 calendar days.

E flagged activities that were only reprogrammed

That is what E looks for: finish pulled earlier with no execution. Reprogramming earlier can be legitimate, but it needs a reason, and E is the list of questions. If the reason exists, it gets recorded; if not, the forecast is optimistic.

Does sensitive data leave the machine

No. The tool does not access the network. The report is a local file with no external reference. An assistant only sees what it is shown, and the synthesis is the only part it writes.

How do I update

Run the installer again. It replaces the skill and keeps a customised template, if there is one. The organisation profile stays where it was saved and is not touched.

Does it work with Primavera P6

The method transfers, but nothing was measured in that format. Reading through a Java library exists as an optional path and the result should be treated as unverified.
